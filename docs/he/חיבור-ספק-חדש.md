# חיבור ספק חדש (Omnibees, Dingus, רשת מלונות)

## מה כבר בנוי

- שכבה אחת שכל המערכת מדברת איתה. כל ספק מתחבר אליה בנפרד.
- חיפוש אצל כל הספקים במקביל. ספק איטי או תקוע לא מעכב את השאר.
- בדיקת מחיר חוזרת לפני הזמנה. אם המחיר עלה, ההזמנה נעצרת.
- אין הזמנה כפולה: לכל הזמנה מספר משלנו, ואותו מספר לא נשלח פעמיים.
- אם הספק לא ענה בזמן ההזמנה: המערכת לא שולחת שוב. היא שואלת את הספק אם ההזמנה נקלטה. אם אין תשובה ברורה, ההזמנה מסומנת "לבדיקה ידנית".
- מספרי כרטיס אשראי לא נשמרים ולא נכתבים ללוג. רק "טוקן" של כרטיס וירטואלי.
- כל פנייה לספק נשמרת בלוג (בלי סיסמאות ובלי כרטיסים). הלוג הזה משמש להוכחה מול הספק.
- ספק שעוד לא עבר אישור (certification) לא יכול לעלות לאוויר. המערכת חוסמת את זה.
- ספק דמה (mock), כדי לבנות ולבדוק את ה-CRM לפני שיש חוזה.

## מה לבקש מכל ספק (Omnibees, Dingus, רשת)

1. חוזה מסחרי: מחירים נטו או עמלה, איך משלמים (כרטיס וירטואלי או קרדיט).
2. תיעוד API לסוכנים/מפיצים (distributor / pull API).
3. סביבת בדיקות (test / sandbox): כתובת, שם משתמש, סיסמה.
4. רשימת המלונות שפתוחים לנו + קוד המלון אצלם.
5. האם אפשר לחפש הזמנה לפי המספר שלנו (חשוב לבטיחות).
6. מגבלת קצב (כמה בקשות בשנייה).
7. תהליך האישור (certification): מה צריך להראות להם.
8. שאלה לכל מלון (RIU, Playa): דרך איזו מערכת הוא מחלק מחירים לסוכנים? Omnibees, Dingus, SynXis, או API משלו?

## הסדר

1. חוזה.
2. פרטי סביבת בדיקות → מכניסים לשרת (לא לקוד).
3. ממלאים פרופיל ספק לפי התיעוד שלהם.
4. בדיקות על סביבת הבדיקות שלהם.
5. הם מאשרים.
6. מעבירים לאוויר.

## עדיין חסר לפני הזמנות אמיתיות

- גיבוי לקובץ ההזמנות. ההזמנות נשמרות עכשיו בקובץ קבוע בשרת ושורדות הפעלה מחדש, אבל אף אחד עוד לא מגבה אותו.
- מסד נתונים (Postgres) במקום הקובץ, רק אם ירוצו שני שרתים במקביל.
- חיבור לספק כרטיסים וירטואליים.
- לחבר את ההתראות לוואטסאפ או למייל. המערכת כבר שולחת התראה (webhook) כשהזמנה מסומנת "לבדיקה ידנית", כשתוצאת ביטול לא ידועה, או כשהמחיר הסופי גבוה ממה שאושר. צריך להגדיר לאן היא נשלחת (ALERT_WEBHOOK_URL).
- Hotelbeds: כרגע חדר אחד בלבד בכל הזמנה. יותר מחדר אחד ייפתח אחרי בדיקה מול המערכת שלהם.
- רשימת מלונות + קודים אצל כל ספק.
